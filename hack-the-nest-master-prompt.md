## Mission

You are our lead implementation agent for Hack The Nest at Eastern Michigan University. Build an original, single-player rocket sandbox inspired by Kerbal Space Program, set on a 1:1 Earth. A judge should be able to modify a rocket, launch it from a recognizable Earth location, stage it, and watch its flight become an orbit. Use the Michigan Space Grant Consortium (MSGC) imagery powered by NASA open data as our preferred visual source. We are using Codex and other AI agents to build the game. The game itself needs no AI service. We have exactly 24 hours from kickoff to submission. Start the clock at kickoff and reserve the last three hours for the packaged demo and submission.

## What the judges should be able to play

| Beat | Acceptance criteria |
| --- | --- |
| Build | Start with a working two-stage Starship-style preset. Swap an engine or tank in a simple stack editor. Immediately see total mass, thrust-to-weight ratio, and estimated delta-v change. Put the upper stage, propellant tank, engine, and separator in a small data-driven catalog. Use original or licensed models. Prefer published vehicle specifications where available and mark estimated or fictional values in the part catalog. |
| Launch and stage | Start at one real-world launch site. Prefer Starbase, Texas if the supplied imagery covers it. If the MSGC dataset is regional, use a representative pad at a clearly identified location in that region. Support manual throttle, pitch, and staging. Provide a tested assisted ascent that acts through those same controls and obeys the same physical limits. Show the stage separate and update thrust and propellant telemetry. |
| Reach orbit | Switch from chase view to a globe view with Earth curvature, an orbit line, and apoapsis and periapsis. Count success after engine cutoff when the vehicle is coasting in a bound orbit whose predicted lowest WGS84 altitude clears the documented orbital target. Use 180 km as the default demo threshold and keep it independent of the atmosphere model. Show a suborbital launch falling back toward Earth when the player misses that goal. |
| Repeat | Include on-screen controls and a one-button reset. Aim for a repeatable 90-second presentation while preserving the real simulation duration. Provide a labeled Demo Mode with verified mission checkpoints and a visible time-rate indicator. |

Once the Earth mission works, show the Moon at an approximate real-scale Earth–Moon distance with a map marker if it is hard to see. A lunar flyby is the first stretch goal. Lunar landing, additional planets, a freeform editor, docking, reentry heating, booster recovery, and campaign progression are post-hackathon work. Cut optional effects and features before cutting the offline build or verified launch-to-orbit sequence.

## Flight physics and georeferencing

- **Treat realism as a flight requirement.** Use full-scale Earth and standard SI units. Keep authoritative state in double precision in a portable library independent of Unreal, rendering, and services. Use fixed simulation steps with render interpolation. Keep one active rocket and integrate its three-dimensional position and velocity with a method that passes step-size convergence checks. Use a simplified attitude controller with finite steering response. Full rigid-body part dynamics are optional after the baseline is verified.
- **Use consistent reference frames.** Define a simplified Earth-centered inertial frame for flight, a rotating Earth-fixed frame for the ellipsoid and atmosphere, and a local east-north-up pad frame. Seed the sitting vehicle with the rotating surface’s inertial velocity. Document the epoch, handedness, rotation rate, and where meters convert to Unreal centimeters. Use WGS84 for the globe, pad placement, and geodetic altitude. Anchor the pad, rocket, and ground track to the same transform. Keep authoritative flight state independent of Unreal's local origin and the render camera.
- **Model Earth and air from references.** Use inverse-square gravity with a sourced Earth gravitational parameter. Use density, pressure, and temperature from the 1976 U.S. Standard Atmosphere or a versioned table sampled from it. Respect the source's altitude convention and documented range. Base drag and dynamic pressure on velocity relative to the rotating atmosphere. Add a sourced or clearly estimated Mach-dependent drag curve after validating the baseline. Report max Q from simulated dynamic pressure. Add Earth oblateness (J2), wind, or lunar gravity after the launch and orbit checks pass and only when there is time to verify them. Document omitted effects and any simplified upper-atmosphere treatment.
- **Model propulsion, mass, and staging together.** Use stage dry mass, usable propellant, and published sea-level and vacuum thrust and specific impulse when available. Keep any interpolation or inferred values documented. Consume propellant consistently with the engine model, shut off exhausted engines, and conserve the surviving stage's position and velocity across separation unless an explicit impulse is modeled. Apply each staging event once. Base assisted ascent on the current simulated state through the same throttle, steering, and staging inputs available to the player. Use the same stage settings in manual and assisted flight.
- **Verify orbit and impact from state.** Compute osculating elements from the simulated state in the inertial frame. Use the visual globe's Earth-fixed transform for current position and for any timestamped ground track. Use a documented geocentric reference radius for quick-look apoapsis and periapsis if needed. For mission success, find the minimum WGS84 altitude over the predicted orbit, with sampling or solver tolerance that resolves a borderline result. Label powered or atmospheric projections as estimates. Use an authored collision pad and an analytic WGS84 surface for basic ground impact, or use independently sourced terrain where available. Treat raster imagery as visual data.
- **Validate the numbers.** Compare a reference coast with the analytic circular period and expected orbital speed. Check energy and angular momentum drift in a drag-free, thrust-free two-body run. Compare a full nominal trajectory at the flight step and half that step, with documented tolerances for cutoff and orbital altitude. Check source density and pressure at several altitudes, frame round trips, fuel cutoff, stage continuity, a falling suborbital trajectory, and a successful launch from the pad. Run the same fixtures on both OSes using numerical tolerances.

Put the exact data name and attribution in the credits and README.
- Bundle the globe image, rocket assets, and representative pad in the standard packaged build. Use imagery that permits bundling. Rehearse from the package with networking disabled. Store any live endpoint settings outside the base mission. Keep credentials out of Git, logs, screenshots, and prompts. If the team separately chooses Google Photorealistic 3D Tiles, treat them as a live display option with the required attribution and content handling. The MSGC/NASA demo must start without a Google key.
- Spend the visual budget on three shots: the low-angle pad and launch, stage separation against the horizon, and a clean orbital reveal. Start with one lit scene, an atmospheric limb, a recognizable rocket silhouette, a controlled Niagara exhaust effect, and readable telemetry. Keep UMG display updates at a modest rate. Add costly lighting or effects only after profiling.
- Target 60 fps at 1080p on the chosen laptop. Provide a low preset and aim for a 33 ms p95 frame time or better on that preset over the rehearsed route. Profile the packaged build rather than the editor. Record CPU and GPU frame times, p50 and p95, resolution, hardware, settings, and first versus repeat load. Measure physics cost separately. Fix measured bottlenecks before adding threading or complex physics. Report the measured result and make comparative performance claims about KSP only if the team runs a comparable benchmark.

## Demo timing and disclosure

- **Use the real flight as the source for Demo Mode.** Record a verified run of the shipping mission from the pad. Save complete simulation snapshots near liftoff, staging, and orbital insertion. Demo Mode can load those snapshots and then resume the simulator. Give the presenter explicit controls such as **Jump to staging** and **Load orbit checkpoint**. Keep a persistent **Demo Mode** label and show the mission time after every jump.
- **Support time acceleration where the model passes the checks.** Advance the same fixed simulation steps during powered flight if the target machine can keep up. Use a verified coast method for higher rates only in suitable unpowered flight. Return to the normal rate around staging, burns, or ground approach as needed. Keep elapsed mission time and rates visible. If an optional cheat changes the state beyond loading a verified snapshot, label the exact override on screen and keep it outside the normal mission and acceptance tests. Use the genuine pad-to-orbit test run as the evidence that orbit works.
- **Prepare a live or continuous-take demo first.** An edited recording is a submission option if the event's organizer or track instructions allow it. If they do, cut uneventful periods and mark time jumps or checkpoint loads. If the rules are unclear, use an unedited capture with labeled in-game shortcuts where permitted, or show the normal run or its in-engine replay. Have a teammate check the submission instructions and record any length limit before capture.

## Team execution and delivery

1. **Hours 0–1.** Start Unreal on macOS, assign a Windows build owner, identify the exact imagery, and start headless flight tests. Make the engine decision at hour 1.
2. **Hours 1–8.** Smoke-test both packages by hour 3 if staying with Unreal. Integrate one rocket and a georeferenced pad, manual controls, and staging. Get a headless assisted ascent to the verified orbit target and produce a runnable build by hour 8.
3. **Hours 8–15.** Connect flight and rendering. Add one part swap, real telemetry, the orbit view, and reset. Rehearse the full route. If behind, defer the Moon and reduce effects before reducing the fidelity of the verified flight path.
4. **Hours 15–21.** Package on both platforms, profile the judging hardware, and polish the camera shots. Generate the real-flight checkpoints and try the 90-second demo. Add the Moon if the main mission is reliable. Freeze features at hour 21.
5. **Hours 21–24.** Run both packaged builds offline from fresh launches, fix blockers, record the demo if required, and verify the submission before the deadline.

### Definition of done

- The packaged macOS and Win64 builds both launch with networking disabled on their respective test machines and run the same assemble, launch, stage, orbit, and reset flow. For the browser fallback, verify the same flow on both OSes. The globe imagery has visible credit, and live imagery failure leaves the local build usable.
- A deterministic nominal mission reaches orbit from the pad with normal flight physics, and a failed mission remains suborbital. The cross-platform numerical checks meet documented tolerances. Demo Mode can reproduce the presentation in about 90 seconds and clearly identifies any checkpoint, time acceleration, or override.
- The README contains exact toolchain and build versions, both packaging and launch procedures, target architectures and test status, asset and imagery credits, controls, the demo script, measured performance, and physics approximations.
